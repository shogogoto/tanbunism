# バックエンドのキャッシュ方針

入力に応じて増えるプロセス全体のキャッシュと、インスタンス内の派生値を区別する。
キャッシュを外す・上限を設けるだけでなく、返却値を利用側が変更できるかも確認する。

## 今回確認した境界

| 処理 | 方針 | 理由 |
| --- | --- | --- |
| `parse2net`の解析結果 | 最大8件のLRU。64Ki文字を超える入力は保持しない | 多数の本文とグラフを常駐させない |
| 解析結果の返却 | キャッシュ内部の`SysNet`をdeep copyして返す | グラフ属性、派生リスト、親テーブルへの変更を隔離する |
| `parse2net_uncached`と`do_print=True` | 毎回解析し、解析結果キャッシュを使わない | 明示的な再解析・デバッグ出力を省略しない |
| `create_parser` | 直近16件のLRU | 呼び出しごとに作られる変換器を無制限に保持しない |
| `get_lookup`・`to_lookup` | 毎回独立した辞書 | 参照解決中の辞書拡張が別リソースへ漏れない |
| Neo4jノードの`to_tanbun`変換 | キャッシュしない | 今回取得した値を使い、DBノードや接続由来のグラフを保持しない |
| クイズの正順・逆順の関係辞書 | 毎回独立した辞書 | 利用側の変更が次のクイズへ混ざらない |
| 日付文字列の`str2edtf` | 最大256件のLRU | 不変な文字列の再利用を残し、件数を制限する |
| `split_pattern` | 最大32件のLRU | 可変のパターン指定を無制限に保持しない |

件数・本文文字数の制限は保守的な初期値であり、プロセスのメモリ量をバイト単位で
保証するものではない。サイズ超過でも解析を拒否せず、キャッシュを迂回する。
大きな本文を繰り返し解析する用途ではCPUとのトレードオフがある。

Pydanticの`frozen=True`は内部の辞書やグラフの変更まで禁止するものではない。
そのため共有結果を直接返さず、`model_copy(deep=True)`で所有権を分ける。
[Pydantic 2.11のコピー仕様](https://github.com/pydantic/pydantic/blob/v2.11.0/docs/concepts/serialization.md#model_copy)
に加え、実行環境の2.11.7の実装と、NetworkXグラフを含む回帰テストでも確認する。

## 維持したものと未検討のもの

- 引数のないルーター・認証コンポーネント・固定パターンのfactoryは、入力件数で増えないので維持する。
- `SysNet`などの`cached_property`は、そのスナップショットと同じ寿命で保持する。
  利用側へ公開する際に、別の呼び出しと可変な派生値を共有しない。
- `Def.dummy`は同じ用語に同じ仮の定義を対応させるfactoryで、生成時にUUIDを持つ。
  単純なLRU化では再生成後の同一性が変わるため、今回は変更しない。
  その保持期間と同一性の設計は別途検討が必要で、すべてのキャッシュを解消したわけではない。

## テスト

`parsing/test_cache.py`で再利用、返却値の独立性、容量、退避後の解放、大きい入力の迂回、
デバッグ出力を確認する。用語辞書・DB変換・クイズ関係辞書にも変更漏れの回帰テストを置く。
最適化を変更する際は値の一致だけでなく、所有権と寿命の契約も維持する。
